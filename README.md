#M1 — Proposal & architectural requirements #
1. System overview 
A one-page description of the proposed system: the problem it solves, who uses it, and why it is 
architecturally interesting. 
2. Stakeholders and concerns 
A table of at least five stakeholders (e.g., end users, administrators, developers, operators, 
business owner, regulators) and each one’s key concerns. 
3. System context 
A context diagram (C4 Level 1) showing the system as a single box, its users, and all external 
systems it interacts with. 
4. Functional requirements 
The main use cases or user stories (8–15), prioritized using MoSCoW. Mark which ones the 
prototype will implement in Milestone 3. 
5. Quality attribute scenarios 
At least five quality attribute scenarios using the six-part form (source, stimulus, artifact, 
environment, response, response measure), covering at least four different quality attributes 
(e.g., performance, availability, security, modifiability, scalability, usability, testability). 
• Response measures must be concrete and testable (e.g., “95% of search requests complete 
in under 500 ms with 200 concurrent users”), not vague (“the system should be fast”). 
6. Constraints 
Technical, business and organizational constraints (e.g., must run on a free cloud tier, must use a 
given language, must integrate with a specific payment API, 12-week deadline). 
7. Architecturally significant requirements (ASRs) 
Rank the requirements from sections 4–6 and justify the top 3–5 as the ones that will most 
influence your architecture, using a utility tree or a prioritized table (business value vs. 
architectural impact: H/M/L).
